* Introduction
*RUMPS* is a re-imagining of MUMPS-style database systems. Rather than store relational tables as SQL does, RUMPS stores *sparse*, *sorted*, *hierarchical trees* of data. Data is addressed by /key/: each /key/ is a list of /subscripts/ in the tree:

#+HTML: <p align="center">
#+HTML:   <img src="stuff/storage-diagram.svg" alt="RUMPS storage model">
#+HTML: </p>

What makes this interesting is that the /logical model/ (hierarchical sparse trees and their operations) and the /physical model/ (B-tree) are essentially the same shape. Operations like =order= (=$ORDER=; "next key in sorted order") are /literally/ what B-trees do. The user thinks in /tree traversal/; there's no impedance mismatch between the user's thought and storage operations.

RUMPS inherits many of MUMPS' core concepts, e.g. collation order, a similar storage model, etc..., but either expands on or diverges wildly from them. See [[./docs/concepts.org][Concepts]] for the full background. If you don't know what MUMPS is, [[https://en.wikipedia.org/wiki/MUMPS][this]] is a good introduction. For a comparison with SQL, see [[./docs/comparison.org][RUMPS vs SQL]].

Key properties:
- *Sparse*: No need to fill gaps or pad; if /only/ keys =1=, =2=, =10= are set, there is no padding for =3= through =9=
- *Sorted*: Iteration always yields keys /in order/; no post-hoc sorting needed, ever
- *Hierarchical*: Theoretically unlimited nesting depth
- *Schema-less*: Structure emerges from keys; no =CREATE TABLE=, no migrations
- *ACID*: Full transactional semantics for writes to globals (see [[./docs/concepts.org#acid-guarantees][ACID guarantees]])
- *Async-native*: Built on =tokio= from the ground up; all I/O is non-blocking

* Use cases
** Where RUMPS is a good fit
*** Sparse, irregular, or schema-less data
This is the core sweet spot. In SQL, every row has every column (even if =NULL=). In RUMPS, absent keys simply don't exist, so there is zero storage overhead for absent fields:

#+begin_src text
; Patient 123 has 3 fields
^PATIENT{123,"NAME"} = "Alice"
^PATIENT{123,"DOB"} = "1990-01-01"
^PATIENT{123,"PHONE"} = "555-1234"

; Patient 456 has completely different fields
^PATIENT{456,"NAME"} = "Bob"
^PATIENT{456,"FAX"} = "555-9999"
^PATIENT{456,"EMERGENCY","NAME"} = "Carol"
^PATIENT{456,"EMERGENCY","PHONE"} = "555-0000"
#+end_src

This makes RUMPS well-suited for:
- Entities with many optional fields (only present keys consume space)
- Survey responses where most questions are skipped
- Feature flags per user or tenant
- Multi-tenant systems with tenant-specific fields
- Rapid prototyping where structure isn't finalized
- Log/event storage with varying payloads
- Or any other domain where "shape" varies between records

There is no need for migrations, =ALTER TABLE=, etc...; you can add or remove new "fields" (subscripts) whenever you want.
*** Hierarchical or nested data
The tree-shaped storage model maps directly to naturally hierarchical data:
- *Medical records* =^PATIENT{id, "VISITS", date, "DIAGNOSIS"}=: nested visits, labs, prescriptions per patient
  - This is, historically and to date, where MUMPS has been popular. Patient records may vary /wildly/ and defining a preset schema is a non-starter
- *Org structures* =^ORG{dept, team, employee}=: traverse by department or drill into individuals
- *File system metadata* =^FS{path, component, ...}=: arbitrary nesting depth
- *Configuration trees* =^CONFIG{section, subsection, key}=: nested settings with natural grouping

One key advantage: no joins required; the hierarchy /is/ the data model.
*** Key-range workloads
Because data is stored in sorted key order, range scans are efficient:
- *Time-series* :: =^LOG{2025, 01, 15, timestamp}=; date-range scans are just prefix iteration
- *Audit trails* :: =^AUDIT{entity, action, time}=; query by entity, then by time
- *Leaderboards* :: Sorted sets come naturally; iterate top N via =order=
*** Document-like access patterns
You can retrieve entire subtrees in one traversal; nested structures map directly to nested keys. If your data looks like JSON, RUMPS can handle it without serializing/deserializing entire documents. RUMPS also specifically gives you the option of storing globs of document-like data via =Value::Json= for when you really want JSON at a particular key path.
*** Low-ceremony applications
When SQL DDL feels like overkill:
- Embedded databases for CLI tools or small services (similar use case to SQLite)
  - By "embedded", I mean embedded into the application, not embedded /devices/. RUMPS requires =std= and =tokio=; it doesn't work for =no_std= or embedded device targets
- Prototypes that may evolve into larger systems
- Situations where you want transactional semantics without schema overhead
** Where RUMPS is a bad fit
*** Flat key-value storage
If you just need =get(key) -> Option<Value>= with no hierarchy or range queries, RUMPS is overkill. A =HashMap= with =RwLock=, =DashMap=, or =sled= will be faster and simpler. RUMPS shines when your keys have /structure/ you want to query.
*** Simple memoization or function caching
Caching pure function results by input hash doesn't need transactions, range queries, or hierarchical access. Use =moka=, =cached=, or a simple LRU cache crate instead.
*** TTL-based expiration
RUMPS has no built-in key expiration. You /can/ implement time-based cleanup via =order= iteration, but it's manual. If you need TTL natively, Redis or =moka= are better fits.
*** Nanosecond-scale hot paths
B-tree traversal and async machinery add overhead vs. lock-free hash maps. For millions of tiny ops/sec on flat data, raw =DashMap= wins. RUMPS is better suited for microsecond-scale structured operations.
*** Relational data with complex joins
MUMPS-style databases excel at hierarchical traversal, not relational algebra. If you need multi-table joins, aggregations, or SQL semantics, use SQLite or Postgres. RUMPS /can/ model relations, but you're hand-rolling the join logic.
*** =no_std= or embedded targets
RUMPS requires =std= and =tokio=. For microcontrollers or =no_std= environments, look elsewhere.
*** Production workloads requiring proven reliability
RUMPS is experimental and under active development. For production systems that need battle-tested reliability, use established alternatives.

* Quick start
** Rust API
1. Get RUMPS somehow
   - *NOTE*: I haven't put any of the RUMPS crates on ~crates.io~ yet, so you'll need to use it as a Git crate
2. Start writing your sweet, sweet data to RUMPS; this is a minimal example: much more explanation is in the [[./docs/operations.org][operations reference]]:
  #+begin_src rust
  use futures::TryStreamExt;
  use rumps::*;

  // NOTE: RUMPS is fully async; currently, it only supports `tokio`
  #[tokio::main]
  async fn main() -> rumps::Result<()> {
      // Create a persistent database; path is a directory
      // (will contain `data.db` + `wal/`)
      let db = Database::create("./my_data").await?;
      // You can later re-open the same directory
      // let db = Database::open("./my_data").await?;

      // Create variable bindings using macros. The `global!` and `local!` macros
      // use `SmolStr` internally, making `.clone()` cheap (no heap allocation
      // for short names). This is useful when moving names into async closures.
      // For runtime-constructed names, use `Name::global(&str)` instead.
      let patients = global!("PATIENT");
      let audits = global!("AUDIT");

      // Writes to globals require a transaction
      db.transaction(|txn| {
          // Cheap clone. All global/local clones are generally cheap, especially
          // in the common case of a short name
          let patients = patients.clone();
          async move {
              // Insert patients out of order
              txn.set(&patients, &key![3, "NAME"], value!("carol")).await?;
              txn.set(&patients, &key![1, "NAME"], value!("alice")).await?;
              txn.set(&patients, &key![2, "NAME"], value!("bob")).await?;
              Ok(())
          }
      }).await?;

      // Transactions can be configured with custom parameters, e.g. timeout,
      // conflict overwrite, etc...
      db.build_transaction()
          .timeout(5000)  // 5 second timeout
          .begin(|txn| {
              let audits = audits.clone();
              async move {
                  txn.set(&audits, &key![1], value!("logged")).await?;
                  Ok(())
              }
          }).await?;

      // All reads work outside transactions
      let name = db.get(&patients, &key![1, "NAME"]).await?;
      assert_eq!(name, Some(value!("alice")));

      // `query` ($QUERY): get next full key in sorted order
      let first = db.query(&patients, None).await?;
      assert_eq!(first, Some(key![1, "NAME"]));

      // `data` ($DATA): check if a node has value/descendants
      let status = db.data(&patients, &key![1]).await?;
      assert_eq!(status, DataStatus::HasDescendants);

      // `collects`: stream records; ALWAYS yields in sorted key order
      // (sorting is inherent to RUMPS data storage)
      let names: Vec<String> = db
          .collects(
              &patients,
              None,
              // Predicate to extract data
              |k, _| k.len() == 2 && k.get(1) == Some(&subscript!("NAME")),
              // Mapping/transformation of data
              |_, v| v.as_ref()?.as_str().map(str::to_uppercase),
          )
          .await?
          .try_collect()
          .await?;

      // Results come out sorted by _key_, _not_ insertion order
      assert_eq!(names, vec!["ALICE", "BOB", "CAROL"]);

      // Not strictly necessary; `Database` has a `Drop` implementation that
      // cleans up resources when the strong `Arc` count is 1. However, to
      // ensure resource cleanup, `Database::close` can be called
      db.close().await?;

      Ok(())
  }
  #+end_src

* Database explorer
The =rumps-explorer= crate provides a TUI executable for browsing RUMPS databases. You can point it at a database directory and navigate the tree structure interactively:

#+begin_src bash
cargo run --package rumps-explorer -- ./path/to/db
#+end_src

The TUI footer explains navigation keybindings, help, etc..., inside the explorer.

This is useful for poking around unfamiliar databases, verifying data after writes, or understanding how data is structured in the tree.

* Performance
All numbers below are on-disk with =SyncMode::OnCommit= (the default), NVMe SSD, ZFS. When =transaction()= returns =Ok=, /the data is really on disk/. Actual speed may vary based on storage hardware and filesystem.

*** Writes
| *Workload*                                   | *Throughput*     |
|--------------------------------------------+----------------|
| Single global, batched (100-1000 ops/txn)  | ~90-95 Kelem/s |
| Single global, batched (10k-100k ops/txn)  | ~73-77 Kelem/s |
| Multi-global (1000 ops across 100 globals) | ~300 Kelem/s   |
| Single =set= (=$SET=), 1 op/txn                | ~14 Kops/s     |

Multi-global writes benefit from RUMPS's sharded node cache: writes to different globals proceed in parallel with reduced lock contention. Larger batches amortize fixed I/O cost (=fsync=, WAL flush), so it is generally better to write to 1,000 key addresses in a single transaction than 100 addresses spread across 10 transactions.

*** Reads and traversal
| *Workload*                                  | *Latency/Throughput*     |
|-------------------------------------------+------------------------|
| Single =get= (=$GET=)                         | ~34 us                 |
| =query= (=$QUERY=), 100 sequential keys       | ~104 us (~960 Kelem/s) |
| =order= (=$ORDER=), 100 sequential subscripts | ~111 us (~900 Kelem/s) |
| =collects=, 1000 entries                    | ~713 us (~1.4 Melem/s) |
| =collects=, 10000 entries                   | ~7.5 ms (~1.3 Melem/s) |

All read operations work outside transactions. Traversal (=query=, =order=, =collects=) yields results in sorted key order with no post-hoc sorting.

*** Deletes
| *Workload*                   | *Latency*  |
|------------------------------+------------|
| =kill= (=$KILL=), subtree (100 nodes)  | ~1.0 ms    |

*** Increment (=$INCREMENT=)
| *Workload*                                  | *Latency/Throughput*     |
|-------------------------------------------+------------------------|
| Single =increment=, 1 op/txn                | ~44 us                 |
| Same key, 1000 ops/txn (counter hot path) | ~320 us (~3.1 Melem/s) |
| 1000 distinct keys/txn                    | ~10.6 ms (~94 Kelem/s) |

Float deltas (integer-to-double promotion) have no measurable overhead versus integer deltas. The hot-key path sustains ~3.1 Melem/s because every operation hits the same B-tree leaf; spreading across 1000 distinct keys drops to ~94 Kelem/s due to per-key traversal cost.

*** In-memory (=Database::in_memory()=)
No WAL, no =fsync=, no disk I/O. Useful for caching, testing, or scratch workspaces where you want transactional semantics without persistence.

**** Writes
| *Workload*                                   | *Throughput*       |
|--------------------------------------------+------------------|
| Single global, batched (100-1000 ops/txn)  | ~590-690 Kelem/s |
| Single global, batched (10k-100k ops/txn)  | ~400-520 Kelem/s |
| Multi-global (1000 ops across 100 globals) | ~870 Kelem/s     |
| Single =set= (=$SET=), 1 op/txn                | ~220 Kops/s      |

One quirk of in-memory mode: per-element throughput /decreases/ for larger batches, which is the opposite of on-disk behavior. On-disk, the fixed I/O cost (=fsync=, WAL flush) is amortized over more operations; in-memory has no I/O to amortize, so you're left with raw =O(n log n)= B-tree insertion cost.

**** Reads and traversal
| *Workload*                                  | *Latency/Throughput*     |
|-------------------------------------------+------------------------|
| Single =get= (=$GET=)                         | ~1.5 us                |
| =query= (=$QUERY=), 100 sequential keys       | ~55 us (~1.8 Melem/s)  |
| =order= (=$ORDER=), 100 sequential subscripts | ~62 us (~1.6 Melem/s)  |
| =collects=, 1000 entries                    | ~520 us (~1.9 Melem/s) |
| =collects=, 10000 entries                   | ~6.8 ms (~1.5 Melem/s) |

**** Deletes
| *Workload*                          | *Latency* |
|-----------------------------------+---------|
| =kill= (=$KILL=), subtree (100 nodes) | ~32 us  |

**** Increment (=$INCREMENT=)
| *Workload*                                  | *Latency/Throughput*     |
|-------------------------------------------+------------------------|
| Single =increment=, 1 op/txn                | ~2.4 us                |
| Same key, 1000 ops/txn (counter hot path) | ~158 us (~6.3 Melem/s) |
| 1000 distinct keys/txn                    | ~1.9 ms (~530 Kelem/s) |

The in-memory hot-key path reaches ~6.3 Melem/s; roughly 2x the on-disk rate, since there is no WAL or =fsync= overhead.

- For more details on sync modes, durability trade-offs, and in-memory ACI guarantees, see the section on ACID guarantees in the [[file:docs/concepts.org][concepts]] doc.
