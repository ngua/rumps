* Overview
RUMPS stores all data using a /persistent B-tree/ backed by a paged storage engine with write-ahead logging. Unlike traditional MUMPS implementations that vary in their storage backends, RUMPS uses a unified architecture where:

- All data (globals and locals) is stored as /complete key paths/ in sorted B-trees
- The same tree structure is used in-memory and on-disk (just serialized differently)
- Persistence is handled via a standard WAL + page cache approach
- Note that most MUMPS implementations use a B+-tree (i.e values only in terminal nodes), whereas RUMPS uses a B-tree (see more below)

This document explains how the storage layer works from the bottom up: from raw pages on disk, through the B-tree structure, up to the logical database operations.

** The MUMPS/RUMPS Data Model
Before diving into implementation details, it helps to understand /what/ we're storing.

In MUMPS (and RUMPS), all data lives in /sparse multi-dimensional arrays/ called "globals" (persistent) and "locals" (ephemeral). A global like =^PATIENT= is essentially a tree where each node can hold both a value /and/ children:

#+begin_example
^PATIENT(123)           = "Active"         ; Patient 123 has a status value
^PATIENT(123,"NAME")    = "John Doe"       ; ...and also has children
^PATIENT(123,"DOB")     = "1974-08-09"
^PATIENT(123,"ADDR")    = "123 Main St"
#+end_example

This creates the logical structure:

#+begin_example
^PATIENT
  └─ 123 = "Active"
      ├─ "ADDR" = "123 Main St"
      ├─ "DOB"  = "1974-08-09"
      └─ "NAME" = "John Doe"
#+end_example

*** Inherent Sorting
All data is /inherently sorted/. The subscripts =[123, "ADDR"]=, =[123, "DOB"]=, =[123, "NAME"]= are stored in order according to RUMPS' /extended collation/:

1. *Booleans*: ~false~ < ~true~
2. *Numbers*: Numeric order (=-10 < 0 < 1.5 < 10 < 100=)
3. *Strings*: Lexicographic order

This means operations like "get the next patient" or "iterate all fields for patient 123" are /naturally efficient/—they're just B-tree range scans.

*** Flat Storage with Hierarchy Tracking
Although the data /appears/ hierarchical (i.e. trie-like to the user), RUMPS stores it in a /flat B-tree/ where keys are complete paths. The key =^PATIENT(123,"NAME")= is stored as a single entry with key ~Key([123, "NAME"])~.

To preserve hierarchy information (needed for operations like =DATA= which asks "does this node have children?"), each value carries a ~has_descendants~ flag:

| *State*      | ~value~   | ~has_descendants~ | =DATA= *result*              |
|--------------+-----------+-------------------+------------------------------|
| Empty        | ~None~    | ~false~           | =NoData= (MUMPS =0=)         |
| Intermediate | ~None~    | ~true~            | =HasValue= (MUMPS =10=)      |
| Leaf         | ~Some(v)~ | ~false~           | =HasDescendants= (MUMPS =1=) |
| Both         | ~Some(v)~ | ~true~            | =Both= (MUMPS =11=)          |

When you insert =^PATIENT(123,"NAME")=, RUMPS automatically creates an ancestor entry for =^PATIENT(123)= with ~has_descendants = true~. This makes hierarchy queries trivial—no tree scanning required.
* General Architecture
RUMPS uses a three-layer architecture that separates concerns between the =Database= abstraction, the B-tree, and on-disk storage:

#+begin_example
┌─────────────────────────────────────────────────────────────────────────────┐
│  DATABASE LAYER                                                             │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Maps variable names (^PATIENT, TEMP) to B-tree roots                       │
│  Handles WAL logging for durability                                         │
│  Coordinates transactions and recovery                                      │
└────────────────────────────────────────┬────────────────────────────────────┘
                                         │
                                         ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  B-TREE LAYER                                                               │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Pure tree operations on NodeIds                                            │
│  Knows nothing about Names or WAL                                           │
│  Just modifies tree structure and marks pages dirty                         │
└────────────────────────────────────────┬────────────────────────────────────┘
                                         │
                                         ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  STORAGE LAYER                                                              │
│  ─────────────────────────────────────────────────────────────────────────  │
│  Page cache with LRU eviction                                               │
│  WAL files (append-only durability)                                         │
│  Bitmap allocator for page management                                       │
│  Global registry (name → root page mapping)                                 │
└─────────────────────────────────────────────────────────────────────────────┘
#+end_example

** Why This Separation?
1. *Database == Logical Coordinator*
   - Knows about variable =Name=s (like =^PATIENT=)
   - Logs /logical/ WAL records that include Names for meaningful recovery
   - Manages namespace mapping with lazy-loading from registry
     - If this were moved down to the B-Tree, we would need to load /all/ global roots immediately into memory

2. *B-Tree == Pure Tree Operations*
   - Operates ONLY on =NodeId=s with zero knowledge of =Name=s or WAL
   - Implements B-tree algorithms (split, merge, search, delete)
   - Only marks pages dirty—never writes to disk directly
   - Simple, testable, focused on tree correctness

3. *Storage == Physical I/O*
   - Handles actual disk reads/writes
   - Manages page cache, WAL files, registry
   - Provides durability guarantees

*Critical rule*: WAL records need variable =Name= s for crash recovery (e.g., "replay =SET= to =^PATIENT="). Only the Database layer has both Names and the B-tree context, so WAL logging /must/ happen there.

* Page Storage
The storage layer organizes the data file as a sequence of fixed-size /pages/ (=4 KB= each). Every disk read or write operates on whole pages—this aligns with how operating systems and SSDs work, making I/O efficient. B-tree nodes, the allocator bitmap, and the global registry are all stored as pages.

** Page Layout
The data file is organized as a sequence of pages:

#+begin_example
┌──────────────────────────────────────────────────────────────────────────┐
│  DATA FILE                                                               │
├──────────────────────────────────────────────────────────────────────────┤
│  Page 0: Superblock (database metadata)                                  │
│  Page 1: Allocator bitmap (which pages are free/used)                    │
│  Page 2: Global registry root                                            │
│  Page 3+: B-tree nodes, overflow pages, etc.                             │
└──────────────────────────────────────────────────────────────────────────┘
#+end_example

*** Superblock (Page 0)
The superblock contains database metadata:

| *Field*           | *Type*  | *Description*                       |
|-------------------+---------+-------------------------------------|
| ~magic~           | ~[u8;4]~| Magic bytes: ~RUMP~                 |
| ~version~         | ~u16~   | Format version                      |
| ~page_size~       | ~u32~   | Page size in bytes (=4096=)         |
| ~page_count~      | ~u64~   | Total pages in file                 |
| ~allocator_root~  | ~u64~   | Page ID of allocator bitmap         |
| ~registry_root~   | ~u64~   | Page ID of global registry          |
| ~wal_sequence~    | ~u64~   | Last checkpointed WAL sequence      |

*** Allocator Bitmap (Page 1+)
Tracks which pages are allocated vs free. Each bit represents one page:

#+begin_example
Byte 0:  [1][1][1][0][0][0][0][0]  ← Pages 0-7 (first 3 used: superblock, allocator, registry)
Byte 1:  [1][1][1][1][0][0][0][0]  ← Pages 8-15 (4 used for B-tree nodes)
...
#+end_example

When allocating, we scan for a =0= bit, set it to =1=, and return that page ID. When deallocating, we set the bit back to =0=.

*** Global Registry (Page 2+)
Maps global names to their B-tree root pages:

#+begin_example
┌────────────────────────────────────────────────────────────────┐
│ REGISTRY PAGE                                                  │
├────────────────────────────────────────────────────────────────┤
│ Header:                                                        │
│   entry_count: u32                                             │
│   next_page: Option<PageId>  (for chaining if > ~100 globals)  │
├────────────────────────────────────────────────────────────────┤
│ Entries (repeated):                                            │
│   name_len: u16                                                │
│   name_bytes: [u8; name_len]                                   │
│   root_page: u64                                               │
│   key_count: u64                                               │
│   last_modified: u64                                           │
└────────────────────────────────────────────────────────────────┘
#+end_example

When the database opens, we /lazily/ load globals from this registry. The first access to =^PATIENT= reads the registry, finds the root page, and caches it.

** Page Cache
Reading from disk for every operation would be painfully slow. The storage layer maintains an LRU (Least Recently Used) page cache:

#+begin_example
┌─────────────────────────────────────────────────────────────────────────┐
│  PAGE CACHE                                                             │
├─────────────────────────────────────────────────────────────────────────┤
│  HashMap<PageId, CacheEntry>                                            │
│                                                                         │
│  CacheEntry:                                                            │
│    - page_data: [u8; 4096]   (the actual bytes)                         │
│    - dirty: bool             (modified since last flush?)               │
│    - last_access: Instant    (for LRU eviction)                         │
│    - pin_count: usize        (prevents eviction while in use)           │
└─────────────────────────────────────────────────────────────────────────┘
#+end_example

*** Read Path
1. Check cache for page
2. On cache hit: return cached data, update ~last_access~
3. On cache miss: read from disk, add to cache (possibly evicting LRU page first)

*** Write Path
Writes /never/ go directly to the data file. Instead:

1. Update page in cache
2. Mark page as ~dirty~
3. During flush: write all dirty pages to disk, clear ~dirty~ flags

This separation enables WAL-based durability without constant disk I/O.

* Write-Ahead Logging (WAL)
The WAL is how RUMPS achieves durability without writing every change to the data file immediately.

** Core Principle
Before any change becomes visible, it must be:

1. Written to the WAL file (append-only, sequential writes)
2. =fsync='d to disk (ensures it survives crashes)

Only /after/ the WAL is durable can we:

3. Apply the change to the in-memory page cache
4. (Eventually) flush dirty pages to the data file

If we crash after step 2 but before step 4, recovery replays the WAL to reconstruct the changes.

** WAL Record Types
#+begin_example
┌────────────────────────────────────────────────────────────────────────┐
│  WAL RECORD TYPES                                                      │
├────────────────────────────────────────────────────────────────────────┤
│  SET { name, key, old_data, new_data }                                 │
│    - Records a value change with undo information                      │
│                                                                        │
│  KILL_ENTRY { name, key, data }                                        │
│    - Records deletion of a single key (subtree kills generate many)    │
│                                                                        │
│  TXN_BEGIN { txn_id }                                                  │
│    - Marks transaction start                                           │
│                                                                        │
│  TXN_COMMIT { txn_id }                                                 │
│    - Marks transaction commit (only committed ops are replayed)        │
│                                                                        │
│  TXN_ROLLBACK { txn_id }                                               │
│    - Marks transaction abort (these ops are skipped on recovery)       │
│                                                                        │
│  CHECKPOINT { wal_sequence, page_count }                               │
│    - Marks a consistent snapshot (allows WAL truncation)               │
└────────────────────────────────────────────────────────────────────────┘
#+end_example

Each record also contains:
- ~sequence~: Monotonically increasing sequence number
- ~crc32~: Checksum for corruption detection
- ~length~: Record size (enables skipping corrupted records)

** WAL File Format
#+begin_example
┌────────────────────────────────────────────────────────────────────────┐
│  WAL FILE: wal/wal-00001.log                                           │
├────────────────────────────────────────────────────────────────────────┤
│  Header:                                                               │
│    magic: [u8; 4] = "RWAL"                                             │
│    version: u16                                                        │
│    segment_id: u64                                                     │
│    prev_segment: Option<u64>                                           │
├────────────────────────────────────────────────────────────────────────┤
│  Records (repeated):                                                   │
│    length: u32                                                         │
│    crc32: u32                                                          │
│    sequence: u64                                                       │
│    record_type: u8                                                     │
│    payload: [u8; ...]                                                  │
└────────────────────────────────────────────────────────────────────────┘
#+end_example

** Group Commit
Writing and =fsync=ing after every single operation would be slow. The WAL uses /group commit/:

1. Operations append records to an in-memory buffer
2. When buffer is full or commit is requested, write entire buffer
3. Single =fsync= covers multiple operations
4. All waiting operations complete together

This amortizes the expensive =fsync= across many operations.

** WAL Rotation
WAL files don't grow forever. When a file reaches the size limit (default =64 MB=):

1. Finish current segment
2. Create new segment file (=wal-00002.log=, =wal-00003.log=, etc.)
3. Continue writing to new segment

Old segments are kept until a checkpoint proves they're no longer needed.

** Checkpointing
A checkpoint flushes all dirty pages to the data file and records a marker in the WAL:

1. Flush all dirty pages to data file
2. =fsync= data file
3. Write ~CHECKPOINT~ record to WAL
4. =fsync= WAL
5. Update superblock's ~wal_sequence~
6. Delete WAL segments older than the checkpoint

After a checkpoint, recovery only needs to replay WAL records /after/ the checkpoint sequence.

** Recovery
On database open:

1. Read superblock to find last checkpointed ~wal_sequence~
2. Open WAL files, find all records after that sequence
3. Identify committed transactions (have ~TXN_COMMIT~ record)
4. Replay only committed operations in sequence order
5. Re-apply to B-tree and page cache
6. Optionally checkpoint to clean up

#+begin_example
WAL on disk after crash:
  [SET ^A(1)=X] [TXN_COMMIT 1] [SET ^B(2)=Y] [SET ^B(3)=Z] <crash>
                      ↑                                        ↑
              Transaction 1 committed               Transaction 2 incomplete

Recovery replays:
  - SET ^A(1)=X ✓ (committed)
  - SET ^B(2)=Y ✗ (no commit)
  - SET ^B(3)=Z ✗ (no commit)
#+end_example

* B-Tree Structure
The B-tree is where the actual key-value data lives. Each global (=^PATIENT=, =^ORDER=, etc.) has its own B-tree.

** Properties
For a B-tree with minimum degree =t= (default =t = 3=):

| *Property*                   | *Value*                                         |
|------------------------------+-------------------------------------------------|
| Keys per node (non-root)     | =t-1= to =2t-1= (i.e., =2-5= for =t=3=)         |
| Children per internal node   | =t= to =2t= (i.e., =3-6= for =t=3=)             |
| Root keys                    | =1= to =2t-1= (can be smaller)                  |
| Leaf depth                   | All leaves at same depth                        |
| Key ordering                 | Sorted ascending within each node               |

** Node Structure
#+begin_example
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│  B-TREE NODE                                                                              │
├───────────────────────────────────────────────────────────────────────────────────────────┤
│  is_leaf: bool                                                                            │
│                                                                                           │
│  keys: Vec<Key>                                            ← Complete paths, sorted       │
│    [Key([1]), Key([1,"A"]), Key([1,"B"]), Key([2])]                                       │
│                                                                                           │
│  values: Vec<NodeData>                                     ← One per key                  │
│    [NodeData{..}, NodeData{..}, NodeData{..}, NodeData{..}]                               │
│                                                                                           │
│  children: Vec<NodeId>                                     ← Empty for leaves, t-2t int.  │
│    [NodeId(5), NodeId(7), NodeId(9), NodeId(12), NodeId(15)]                              │
│           ↓         ↓         ↓          ↓           ↓                                    │
│         <1       1..1A     1A..1B      1B..2        >2                                    │
└───────────────────────────────────────────────────────────────────────────────────────────┘
#+end_example

*** NodeData

Each key has associated ~NodeData~:

#+BEGIN_SRC rust
pub struct NodeData {
    value: Option<Value>,     // The actual data (if any)
    has_descendants: bool,    // Does this path have children?
}
#+END_SRC

*** NodeId
Nodes are referenced by ~NodeId~ (a =u64= page ID), not by pointers. This enables:
- *Lazy loading*: Load nodes from disk on demand
- *Page cache integration*: LRU eviction when memory is tight
- *Unified model*: Same structure for globals (disk) and locals (memory)

** B-Tree vs B+-Tree
RUMPS uses a proper /B-tree/, not a B+-tree. The difference:

- *B+-tree*: Data only in leaves, internal nodes just hold routing keys
- *B-tree*: Data in /all/ nodes (internal and leaf)

We chose B-tree because:

1. MUMPS nodes can have both values AND children (intermediate nodes with data)
2. Splitting/merging naturally handles the value, not just the key
3. Slightly fewer nodes overall (data isn't duplicated in leaves)

** Operations
*** SET (Insert/Update)
#+begin_example
SET ^PATIENT(123,"NAME") = "John Doe"

1. Ensure ancestors exist:
   - Key([123]) must exist with has_descendants=true

2. Find or create target key:
   - Navigate tree, splitting full nodes proactively
   - Insert Key([123,"NAME"]) with value

3. Handle root split if needed:
   - If root becomes full, split and create new root
#+end_example

*** GET (Retrieve)
#+begin_example
GET ^PATIENT(123,"NAME")

1. Start at root
2. Binary search for key in current node
3. If found: return value
4. If not found:
   - If leaf: return None
   - If internal: descend to appropriate child, repeat
#+end_example

*** KILL (Delete Subtree)
#+begin_example
KILL ^PATIENT(123)   ; Removes patient 123 and ALL their fields

1. Find all keys with prefix Key([123])
   - Key([123])
   - Key([123,"ADDR"])
   - Key([123,"DOB"])
   - Key([123,"NAME"])

2. Delete each key (deepest first to minimize rebalancing)

3. Update ancestor has_descendants flags if no siblings remain

4. Rebalance (merge/borrow) as needed
#+end_example

*** ORDER (Next Key)
#+begin_example
ORDER(^PATIENT(123)) → 124   ; Next patient after 123

1. Find Key([123]) in tree
2. Return next key in sorted order: Key([124])
3. Caller extracts subscript: 124
#+end_example

** Node Splitting
When a node reaches =2t-1= keys, split at the median:

#+begin_example
Before (min_degree=3, 5 keys):
  Node: [10, 20, 30, 40, 50]
              ↑
           median

After:
  Left:   [10, 20]
  Median: 30 → promoted to parent (WITH its value!)
  Right:  [40, 50]
#+end_example

Note: The median's /value/ is also promoted. This is B-tree semantics—the value moves with the key, not just a separator.

** Node Merging
When siblings are both at minimum size, merge them:

#+begin_example
Before:
  Parent: [..., 30, ...]
               / \
  Left:   [10, 20]   Right: [40, 50]

After (merged into left):
  Merged: [10, 20, 30, 40, 50]
                   ↑
          separator from parent
#+end_example

The separator key (=30=) and its value come down from the parent.

* Globals vs Locals
RUMPS distinguishes two namespaces:

| *Type*  | *Prefix* | *Storage*  | *Persistence* | *WAL Logged* |
|---------+--------+--------------+-------------+------------|
| Globals | =^=    | Disk-backed  | Yes         | Yes        |
| Locals  | (none) | Memory-only  | No          | No         |

** Globals
- These are represented with a caret-prefix, e.g. =^NAME=
- Persisted to disk via WAL and page cache
- Lazy-loaded from registry on first access
- Survive database restarts
- Require explicit transactions for writes

** Locals
- These are represented /without/ a caret-prefix, e.g. =^NAME=
- Memory-only, never touch disk
- Discarded when database closes
- Fast, ephemeral storage for session state
- No transaction overhead

Both use the /same B-tree implementation/—the only difference is whether the storage layer writes to disk.

* Transactions
All writes to globals /must/ occur within transactions. This ensures:

- *Atomicity*: All operations succeed or all fail
- *Durability*: Committed changes survive crashes
- *Consistency*: Database is never left in partial state

** Transaction Flow
#+begin_example
1. Begin transaction
   - Allocate TransactionId
   - Log TXN_BEGIN to WAL

2. Execute operations
   - Each SET/KILL logs to WAL (with undo info)
   - Changes applied to in-memory page cache
   - Pages marked dirty

3a. Commit
   - Log TXN_COMMIT to WAL
   - fsync WAL (durability point!)
   - Flush dirty pages to data file (can happen later)

3b. Rollback
   - Log TXN_ROLLBACK to WAL
   - Undo changes using old_data from WAL records
   - Clear dirty flags
#+end_example

** Sync Modes
The storage layer supports different durability/performance tradeoffs:

| *Mode*      | *Behavior*                         | *Durability* | *Performance* |
|-------------+------------------------------------+--------------+---------------|
| =Immediate= | =fsync= after every WAL write      | Highest      | Slowest       |
| =OnCommit=  | =fsync= only on transaction commit | Good         | Good          |
| =Periodic=  | =fsync= every N ms or N records    | Depends      | Best          |

Default is ~OnCommit~—you get durability when you commit, with group commit for efficiency.

* File Layout
A RUMPS database directory looks like:

#+begin_example
mydb/
├── data.db            # Main data file (pages: superblock, allocator, registry, B-trees)
└── wal/
    ├── wal-00001.log  # WAL segment 1
    ├── wal-00002.log  # WAL segment 2 (current)
    └── ...
#+end_example

Concurrent access is managed via =RwLock= on the file handle—no separate lock file.

** Data File Growth
The data file grows as needed:

1. Start with superblock + allocator + registry = 3 pages
2. Each new B-tree node allocates a page
3. File grows in chunks (default =1 MB=) to reduce fragmentation
4. Deallocated pages are reused (tracked in allocator bitmap)

** WAL Cleanup
Old WAL segments are deleted after checkpoints:

1. Checkpoint records the current WAL sequence
2. Any segment where /all/ records are before the checkpoint sequence is safe to delete
3. Automatic cleanup runs after each checkpoint

* Limits
** Maximum Database Size
The allocator bitmap uses a three-level indirect scheme similar to Unix inodes:

| *Level*          | *Bitmap Pages*    | *Calculation*            |
|------------------+-------------------+--------------------------|
| Direct           | 400               | Stored in superblock     |
| Single indirect  | 512               | =PAGE_SIZE / 8=          |
| Double indirect  | 262,144           | =512 × 512=              |
| *Total*          | *263,056*         |                          |

Each bitmap page tracks =PAGE_SIZE × 8 = 32,768= pages. So, with the default =4 KB= page size:

- *Max pages*: =263,056 × 32,768 ≈ 8.6 billion=
- *Max database size*: =~32 TiB=

Note that these limits apply to the /default/ settings. Page size can be increased by settings the ~RUMPS_PAGE_SIZE~ env var at compile time.

** Maximum Globals
The global registry uses page chaining—when one page fills up, a new page is allocated and linked. This means there's no hard limit on the number of globals.

Each registry page holds ~4070 bytes of entries. Entry size is =10 + name_length= bytes, so:

- With 10-character names: ~200 globals per page
- With 20-character names: ~135 globals per page

Since pages chain automatically, you can have millions of globals if needed.

* Summary
RUMPS storage is a fairly standard "pages + WAL + B-tree" architecture, but tailored for MUMPS semantics:

| *Component*   | *Purpose*                                        |
|---------------+--------------------------------------------------|
| Pages         | Fixed-size I/O units, managed by LRU cache       |
| Superblock    | Database metadata (format version, pointers)     |
| Allocator     | Bitmap tracking free/used pages                  |
| Registry      | Maps global names to B-tree roots                |
| B-tree        | Sorted key-value storage with hierarchy tracking |
| ~NodeData~    | Value + ~has_descendants~ flag per key           |
| WAL           | Durability via write-ahead logging               |
| Transactions  | ACID semantics for global writes                 |

The key insight is that MUMPS's "sparse multi-dimensional arrays" map naturally to B-trees with complete-path keys. The ~has_descendants~ flag bridges the gap between flat storage and hierarchical semantics, enabling efficient =DATA=, =ORDER=, and =KILL= operations.
